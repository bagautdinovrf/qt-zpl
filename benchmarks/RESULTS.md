# Производительность QtZpl — 2026-10-07

Пути `build_*` ниже сохранены как часть исторического протокола. С 2026-10-09
эти каталоги размещаются в `build_agent/` с прежними именами; например,
`build_agent_release/` теперь находится в `build_agent/build_agent_release/`.
Актуальные команды приведены в [README](README.md).

Выбран и оставлен **вариант B**: оптимизации парсера, Code 128, Font 0,
непрозрачной GF-графики, QR и таблиц коррекции PDF417/MaxiCode.
Публичный API не изменён. Все 69 доступных fingerprints парсинга и растров
совпали с исходной версией. Это сохранение текущего результата, а не заявление
об устранении известных отличий от Labelary.

Числа, разброс, параметры всех 105 кейсов, результаты повторных серий и
SHA-256 изменённых production-файлов сохранены в

## Условия измерений

- Исходный код: `4bdc94fcfbf1d409a792eb7958a057eae6d2b760`.
- Windows, Intel Core i7-11700, 8 ядер / 16 логических процессоров;
  Qt 6.11.2, MSVC 19.44.35228.0, Release `/O2 /Ob2`, shared QtZpl.
- Qt backend `windows`; один поток; прогретые входы и статические таблицы;
  выделение памяти и уничтожение результатов входят в замеры.
- Полный набор: 105 кейсов, по 9 пакетов с целевой длительностью 50 мс.
  Отдельно измерены 21 parser, 34 render, 14 end-to-end, 28 encoder и 8 component кейсов.
- Для выбора варианта повторены 23 ключевых кейса в порядке
  `исходная → A → B → B → A → исходная`: по 7 пакетов с целевыми 100 мс.
  Таблицы ниже используют медиану двух медиан каждой версии.
- На рабочей машине есть фоновая нагрузка. В повторных сериях у большинства
  алгоритмов MAD около 1–4%; отдельные raster/font замеры шумнее. Разницу
  порядка нескольких процентов не считаем доказанным выигрышем.
- Это сравнение времени этапов и отдельных компонентов, а не sampling-профиль
  с измеренной долей каждого стека. Статическая и Debug-сборки проверены на
  корректность; их времена не смешиваются с Release shared.

## Какие варианты проверены и почему выбран B

**A** убирает лишнюю работу без изменения алгоритма изображения:

1. `src/parser.cpp`: FD/FV и команды с необрабатываемым текстом обходят
   `split(',')`; GF разбирает только заголовок. Для обычных двух hex-цифр FH
   используется прямое преобразование, для необычных пар сохранён Qt fallback.
   Пустые параметры, исходный текст, смещения и восстановление неполных
   заголовков сохраняются.
2. `src/barcode_encoders.cpp`: в Subset C достаточно проверить следующую
   пару цифр. Повторное сканирование всего хвоста делало Code 128 auto
   квадратичным по длине серии; новый путь линейный.
3. `src/renderer.cpp`: один ленивый `QRawFont` на вызов `render(Document)`
   вместо нового font engine для каждого поля. Контекст принадлежит вызову,
   не разделяется между потоками и действует для всех его этикеток.
4. Непрозрачный GF записывает установленные биты прямо в clipped scanlines.
   Нулевые биты сохраняют фон. Полупрозрачные цвета используют прежний
   QPainter SourceOver. Координаты clipping вычисляются в 64 битах.

**B** добавляет следующие улучшения к A:

| Изменение | A | B | Решение |
|---|---:|---:|---|
| Glyph-кэш, 100 одинаковых полей Font 0 | 16,891 мс | 14,747 мс | Оставлен, 1,15× к A |
| Glyph-кэш, 100 разных полей Font 0 | 17,611 мс | 14,728 мс | Оставлен, 1,20× к A |
| QR 1024 байта, однократный ECC/placement | 6,896 мс | 5,057 мс | Оставлен, 1,36× к A |
| PDF417 ECC level 8, неизменяемые коэффициенты | 0,960 мс | 0,304 мс | Оставлен, 3,16× к A |
| MaxiCode, неизменяемые RS10/RS20 | 14,110 мкс | 10,129 мкс | Оставлен, 1,39× к A |

Контуры Font 0 кэшируются в пространстве самого шрифта по glyph index,
поэтому один контур подходит разным размерам и поворотам. Кэш ограничен
числом глифов встроенного шрифта и живёт один render-вызов. Для `^FO` N/R
также убран расчёт ширины, который не использовался при позиционировании.

QR продолжает проверять все восемь масок с прежним `zebraQrPenalty` и тем же
правилом разрешения равных оценок. Локальный callback в vendored qrcodegen
позволяет один раз выполнить кодирование/ECC/placement. Подмена автоматического
выбора фиксированной маской не является вариантом оптимизации с тем же выводом;
fixed-mask кейс служит только измерением компонента.

PDF417 лениво создаёт неизменяемые таблицы отдельно для каждого уровня.
Все девять уровней вместе содержат 1022 коэффициента, около 4 КиБ данных.
MaxiCode разделяет только неизменяемые GF/RS-таблицы; рабочие буферы локальны.

B не выигрывает у A на каждой этикетке: `barcodes` дал 21,736 → 22,296 мс,
FedEx Ground — 8,988 → 9,092 мс. Эти небольшие различия сопоставимы с шумом,
а повторяемые выгоды видны на целевых текстовых и encoder-нагрузках.

## Оставшиеся узкие места и следующие шаги

1. **Перенос длинного Font 0 текста в `^FB`.** Синтетическое слово на 1100
   символов занимает около 44 мс в полном B-прогоне. `layoutBlockLines`
   повторно измеряет растущие префиксы/остатки через glyph mapping и advances.
   Следующий эксперимент: единожды вычислять префиксные advances для Font 0,
   затем искать границы строк без повторного измерения. Нужно сохранить
   округление, Unicode, hanging indent и правила переноса; эффект ещё не измерен.
2. **Растеризация MaxiCode.** Полный одиночный рендер около 19,6 мс, само
   кодирование около 0,01 мс. `rasterizeMaxiCode` строит примерно 15 МБ растра
   в масштабе 10×, рисует кольца и выбирает точки уменьшенного изображения.
   Следующий эксперимент — вычислять те же выбранные точки напрямую либо
   заранее подготовить геометрию. Любое изменение обязано сохранить точные
   Labelary-пиксели. Кэш RS не решает эту основную стоимость.
3. **Выделение и заполнение QImage.** Probe 812×1218: около 1,62 мс для
   allocate+fill против 0,109 мс для refill существующего буфера. Это измерение
   повторно используемой горячей памяти, не гарантированный выигрыш нового API.
   Существующий API возвращает независимые изображения; возможный `renderInto`
   потребует отдельного контракта владения. Для текущего API новый буфер остаётся
   необходимым.
4. **Оценка восьми QR-масок.** После ускорения QR auto1024 всё ещё около
   5,06 мс против 0,61 мс fixed-mask. Разность включает нанесение/снятие масок,
   преобразование матриц и penalty; это не чистая измеренная доля penalty.
   Следующий эксперимент — оценивать маски без копирования в промежуточный
   `Matrix`, сохранив тот же score. Отказ от проверки масок изменит результат.
5. **Обычный парсер.** Прямой эффект новых правок прежде всего относится к
   большим FD/FH. Для дальнейшего ускорения обычных этикеток можно сравнить
   параметрические `QStringView` и диспетчеризацию opcode, сохранив исходники
   команд и пустые параметры. На тяжёлых этикетках сейчас приоритет у рендера.
