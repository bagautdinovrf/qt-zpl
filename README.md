# QtZpl

Нативная библиотека на C++23 и Qt 6.11 для разбора ZPL и растрового рендеринга этикеток. Библиотека не зависит от среды выполнения Go.

```cpp
auto result = QtZpl::render(zpl);
if (result) {
    const QList<QImage>& labels = result->labels;
}
```

По умолчанию парсер работает в отказоустойчивом режиме: неподдерживаемые команды сохраняются в публичной модели документа и добавляются в список диагностик.

Цель совместимости: каждый пример, опубликованный в
[веб-демо go-zpl](https://stirlingmarketinggroup.github.io/go-zpl/), должен
локально отрисовываться с той же геометрией и видимым содержимым, что и
проверенный эталон [Labelary](https://labelary.com/). Демо go-zpl даёт только
ZPL-фикстуры (`tests/corpus/go-zpl-demo/`); эталонные PNG — bitonal Labelary
(`tests/golden/go-zpl-demo/`). Это критерий приёмки; перечень реализованных
команд пока не обеспечивает полную пиксельную совместимость со всем
демонстрационным набором.

Реализован нативный рендеринг следующих штрихкодов:

| Команда | Символ |
|---|---|
| `^BC`, `^B3`, `^BA`, `^BK` | Code 128, Code 39, Code 93, Codabar |
| `^BE`, `^B8`, `^BU`, `^B9` | EAN-13, EAN-8, UPC-A, UPC-E |
| `^B2`, `^BI` | Interleaved 2 of 5, Industrial 2 of 5 |
| `^BR` | GS1 DataBar: Omnidirectional, Truncated, Stacked, Stacked Omnidirectional, Limited, Expanded / Expanded Stacked (типы 1–6) |
| `^BQ`, `^BX` | QR Model 2, квадратный и прямоугольный DataMatrix ECC200 |
| `^B7`, `^BF` | PDF417, в том числе усечённый; MicroPDF417, все 34 режима |
| `^BO`, `^B0`, `^BD` | Aztec (включая rune), MaxiCode, режимы 2–6 |

Каждый кодировщик проверяет данные и возвращает диагностику вместо
подмены неподдерживаемого варианта другим штрихкодом. GS1 DataBar composite
(типы 7–12), Aztec ECI и structured append пока не реализованы.
Для Code 128
поддерживаются стандартные режимы Subset B, автоматический режим `A`, строгий
режим числовых пар `C`, GS1-128 режим `D` и управляющие последовательности Zebra.
В режиме `D` скобки и пробелы исключаются из данных, добавляется ведущий FNC1,
а `>8` разделяет поля переменной длины; числовые пары упаковываются автоматически.
Поддерживаются режим `U` и необязательная контрольная цифра UCC Mod 10. GS1
DataMatrix выбирается идентификатором формата `1`; настроенный символ
экранирования поддерживает `x1` для FNC1 и десятичные последовательности байтов
`xdNNN` (например, `|d029` для разделителя GS).

Для обычного ECC200 кодировщик дополнительно использует C40/Text, когда это
позволяет выбрать меньший символ или выполнить явно заданный размер. Проверенные
ASCII/GS1-векторы сохраняются, если они помещаются в выбранную ёмкость.
Полная оптимизация переключений режимов пока не реализована; оставшиеся
различия и точные эталоны перечислены в
`tests/golden/datamatrix-diagnostics/README.md`.
Масштаб `^BQ` также меняет ширину модулей последующих штрихкодов, включая
PDF417; `^BY` переопределяет это значение, а `^BX` сохраняет его.

`^LT` задаёт вертикальное смещение всей этикетки; `^PM` отражает готовую
этикетку по горизонтали; `^LR` меняет режим наложения последующих полей
на обратный (в том числе поверх уже нарисованных полей). `^FR` действует на
одно поле. `^FP` управляет горизонтальным, вертикальным или обратным
направлением текста и межсимвольным интервалом независимо от `^FW`.

`^FO` задаёт верхнюю привязку поля, `^FT` — базовую линию текста, основание
полос штрихкода либо нижний край графики. Парсер сохраняет пропущенные
координаты `^FT` для продолжения предыдущего текста; числовое выравнивание
`0`/`1`/`2` и значение по умолчанию из `^FW` хранятся отдельно от `^FB`.
Эталоны новых команд и позиционирования находятся в `tests/golden/extensions/`
и каталогах соответствующих кодировщиков. PNG получены непосредственно
от Labelary с `X-Quality: Bitonal`; обычная проверка работает без сети.
Если ширина выходного изображения отличается от `^PW`, область печати
центрируется по горизонтали до применения `^PO` и `^PM`, как в Labelary.

Режим GS1-128 `D` проверяется по кодовым словам и пиксельному совпадению с
синтетическими bitonal-эталонами Labelary в обычной и повернутой (`B`) ориентациях.
Эталоны `tests/golden/code128-gs1-*.png` и `font0-block-b-labelary-bitonal.png`
получены 2026-10-07 через API 12 dpmm с размером `1.9737x3.9474` дюйма
(600×1200 точек) и заголовком `X-Quality: Bitonal`. Соответствующие `.zpl`
сохранены рядом; обычные тесты не обращаются к сети. Эталон текстового блока
проверяет привязку и центрирование; полное пиксельное совпадение Font 0 пока
остаётся отдельной нерешённой задачей.

Font 0 рисуется из контуров встроенного Triumvirate Cond Bold. Высота и ширина
масштабируются независимо в координатах принтера; системные шрифты и
`QFont::setStretch` для него не используются. Базовая линия `^FO` равна
`floor(0,75 × высота)`, а `^FT` задаёт её непосредственно. Повороты учитывают
полную высоту и суммарную ширину символов, сохраняя выносные элементы.
Семь пар размеров из этикетки проверяются по синтетическим латинским и
кириллическим `^FO`/`^FT`-эталонам `font0-h*-w*`. Они получены 2026-10-07
через Labelary 12 dpmm, размер `7.89474x3.9474`, `X-Quality: Bitonal`
(2400×1200 точек). Различия сглаживания/привязки контуров к пиксельной сетке
по сравнению с Labelary пока остаются; строгие визуальные тесты не ослаблены.

Сравнение встроенных контуров с Font 0 в PDF Labelary (2026-10-07)
показало различия самих глифов, а не только привязки или общего масштаба.
Например, у `e`, `o` и `g` отличаются контуры; дефис в Labelary имеет
ширину продвижения около 0,903 em против 0,600 em у встроенного шрифта.
Поэтому расхождение `hello.zpl` нельзя устранить одним смещением `^FO`.

Проверка `qtzpl_font_glyphs_tests` охватывает 371 уникальный символ:
латиницу и кириллицу обоих регистров, `Ёё`, знаки препинания и распространённые
спецсимволы. Сохранены исходные bitonal-атласы Labelary, добавлены изолированные
обучающие и проверочные атласы, в том числе с разной высотой и шириной,
привязками `^FO`/`^FT` и поворотами. Отчёт `font-glyph-results.json` в
каталоге тестового EXE содержит сравнения отдельных глифов, границы
чернил и число отличающихся пикселей. Для 54 символов, отсутствующих у
Labelary в этом репертуаре, проверяется явная диагностика. Эти тесты фиксируют оставшийся
дефект Font 0, а не разрешают его порогом похожести.

Отдельный [исследовательский набор Font Zero](third_party/font0-native/README.md)
собирается из 12 семейств под OFL 1.1 и собственных контуров. Для каждого
глифа сохраняется происхождение и рецепт редактирования; доступны TTF,
экспорт SVG и визуальный отчёт. Кандидат пока не заменяет встроенный шрифт:
полное совпадение с Labelary не достигнуто. Независимый сплошной корпус
`tests/golden/font0-size-sweep/` проверяет целые размеры 4–512 включительно
при равных высоте и ширине. Его получение и полный прогон запускаются
отдельными инструментами; обычные тесты остаются полностью локальными.

Font A и стандартные подписи Code 128/93, Interleaved/Industrial 2 of 5
используют встроенный производный DejaVu Sans Mono и нативный FreeType.
Генератор `tools/generate_font_a.py`, параметры и лицензия сохранены в
`third_party/font-a-native/`; генерация шрифта не требуется при сборке.
Растеризация применяет TrueType hints до горизонтального растяжения.
На Windows используется FreeType из Qt без дополнительной DLL; если Qt
собран с системным FreeType, CMake требует пакет разработки FreeType.

`^FH` при `^CI28` декодирует последовательности UTF-8, включая смешение
прямого Unicode и шестнадцатеричных символов. Некорректные последовательности
сохраняются в исходном виде с диагностикой `invalid-field-encoding`.

`FieldData` хранит два представления одного поля: `data` для текста и
`std::optional<QByteArray> bytes` для байтовых кодировщиков. `bytes` содержит
данные после `^FH`, но до обработки управляющих последовательностей штрихкода.
При `^CI28` прямой Unicode преобразуется в UTF-8, а hex-последовательности
всегда сохраняют заданные байты. Для остальных `^CI` сохраняется прежнее
однобайтовое представление символов U+0000…U+00FF; это не реализация всех
кодовых страниц Zebra. Если без потерь получить байты нельзя, `bytes` равно
`std::nullopt`; пустое поле имеет доступный пустой массив.

DataMatrix, QR, PDF417, MicroPDF417, Aztec и MaxiCode получают `bytes`
напрямую. Для Unicode в этих штрихкодах указывайте `^CI28`, для отдельных
двоичных байтов — `^FH`. Даже при некорректном UTF-8 точные байты `^FH`
доступны двоичному кодировщику; предупреждение парсера и исходный текст
сохраняются. Текстовые поля и ограничения алфавитов линейных штрихкодов
не меняются. В ручном режиме QR `Bdddd` длина измеряется в байтах.

Добавление `bytes` меняет двоичную раскладку публичной модели: приложения,
использующие библиотеку, нужно пересобрать вместе с ней.

## Сборка

### Windows (рекомендуется)

Скрипт `tools/build_helper.py` сам поднимает окружение Qt 6.11 и MSVC 2022 и
вызывает CMake/Ninja.

**Без параметров** — собирает Debug и Release в отдельных каталогах, без тестов:

```text
py -3 tools/build_helper.py
py -3 tools/build_helper.py all --clean
```

Каталоги: `build_agent_debug`, `build_agent_release`.

**Одна конфигурация** — укажите `--config` (каталог подбирается автоматически):

```text
py -3 tools/build_helper.py all --clean --config Debug
py -3 tools/build_helper.py test --config Debug
py -3 tools/build_helper.py build --config Debug --target QtZpl

py -3 tools/build_helper.py all --clean --config Release
py -3 tools/build_helper.py build --config Release --target QtZpl
```

Подробный протокол QtTest сохраняется в `build_agent_debug/tests/test_results.txt`
(или в соответствующем каталоге другой конфигурации), включая строки ошибок.

Свой каталог сборки — только если нужен нестандартный путь:

```text
py -3 tools/build_helper.py build --config Release --build-dir build_custom
```

Повторная сборка без переконфигурации:

```text
py -3 tools/build_helper.py build --config Debug
py -3 tools/build_helper.py build --config Release
```

### Установка в другой проект

```text
set QTZPL_ROOT=C:\QtZpl\Release
py -3 tools/build_helper.py install --clean --config Release --build-dir build_agent_release --install-prefix C:\QtZpl\Release
```

Debug-установка — `--config Debug`. Другой kit Qt — `--qt-version` и `--compiler`.

### Ручная сборка (CMake)

Если окружение Qt и MSVC уже настроено в терминале:

```text
cmake -S . -B build_debug -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_PREFIX_PATH=C:/Qt/6.11.1/msvc2022_64
cmake --build build_debug
ctest --test-dir build_debug --output-on-failure

cmake -S . -B build_release -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_PREFIX_PATH=C:/Qt/6.11.1/msvc2022_64
cmake --build build_release
```

По умолчанию в `build_helper.py` используется Qt **6.11.2**, комплект **msvc2022_64**.
Параметры `--qt-version` и `--compiler` переключают другой kit из `C:\Qt`.

## Бенчмарки

```text
py -3 tools/build_helper.py benchmark --config Release
py -3 tools/build_helper.py benchmark --benchmark-filter algorithm/
```

Стенд измеряет парсинг, рендер, полный конвейер и внутренние алгоритмы на
локальном корпусе; JSON сохраняется в каталоге сборки. Методика и сравнение
версий описаны в [benchmarks/README.md](benchmarks/README.md), измеренные
результаты оптимизаций — в [benchmarks/RESULTS.md](benchmarks/RESULTS.md).
Новые команды, проверка глифов и 179 сценариев текущей версии описаны в
[отдельном отчёте](benchmarks/COMMAND-EXTENSIONS-2026-10-07.md).

## Примеры рендеринга

Пример `qtzpl_gallery` создаёт несколько PNG-файлов из реальных строк ZPL:

```text
py -3 tools/build_helper.py gallery
```

Сгенерированные примеры сохраняются в каталоге `examples/rendered`.

Для рендеринга собственного ZPL вставьте его в переменную `ZPL` в корневом
файле `render_helper.py`, затем выполните:

```text
py -3 render_helper.py
```

Каждый блок `^XA...^XZ` сохраняется отдельным файлом `rendered/label_N.png`.

### Сравнение с Labelary golden

Утилита `qtzpl_compare_golden` рендерит ZPL и сравнивает результат с эталонным
PNG (ink bounds, число расхождающихся пикселей, Jaccard, diff-overlay):

```text
py -3 tools/build_helper.py build --config Debug --target qtzpl_compare_golden

build_agent_debug\examples\qtzpl_compare_golden.exe ^
  tests\corpus\go-zpl-demo\hello.zpl ^
  tests\golden\go-zpl-demo\hello-page-1-labelary-bitonal.png ^
  build_agent_debug\hello-actual.png ^
  build_agent_debug\hello-diff.png ^
  --width 812 --height 609 --dpi 203 --ignore-label-home
```

Параметры `--width`, `--height`, `--dpi` и `--ignore-label-home` берите из
`tests/corpus/go-zpl-demo/manifest.json` для соответствующей фикстуры. На
2026-08-12 для `hello.zpl` QR совпадает с Labelary, а текст Font 0 (`^A0` при
`^FO`) — нет; см. `AGENTS.md`.
