# QtZpl

Нативная библиотека на последнем поддерживаемом стандарте C++ (latest) и Qt 6.11 для разбора ZPL и растрового рендеринга этикеток. Библиотека не зависит от среды выполнения Go.

```cpp
auto result = QtZpl::render(zpl);
if (result) {
    const QList<QImage>& labels = result->labels;
}
```

По умолчанию парсер работает в отказоустойчивом режиме: неподдерживаемые команды сохраняются в публичной модели документа и добавляются в список диагностик.

Цель совместимости: каждый пример, опубликованный в
[веб-демо go-zpl](https://stirlingmarketinggroup.github.io/go-zpl/), должен
локально отрисовываться с той же геометрией и видимым содержимым, что и
проверенный эталон [Labelary](https://labelary.com/). Демо go-zpl даёт только
ZPL-фикстуры (`tests/corpus/go-zpl-demo/`); эталонные PNG — bitonal Labelary
(`tests/golden/go-zpl-demo/`). Это критерий приёмки; перечень реализованных
команд пока не обеспечивает полную пиксельную совместимость со всем
демонстрационным набором.

Реализован нативный рендеринг следующих штрихкодов:

| Команда | Символ |
|---|---|
| `^BC`, `^B3`, `^BA`, `^BK` | Code 128, Code 39, Code 93, Codabar |
| `^BE`, `^B8`, `^BU`, `^B9` | EAN-13, EAN-8, UPC-A, UPC-E |
| `^B2`, `^BI` | Interleaved 2 of 5, Industrial 2 of 5 |
| `^BR` | GS1 DataBar: Omnidirectional, Truncated, Stacked, Stacked Omnidirectional, Limited, Expanded / Expanded Stacked (типы 1–6) |
| `^BQ`, `^BX` | QR Model 2, квадратный и прямоугольный DataMatrix ECC200 |
| `^B7`, `^BF` | PDF417, в том числе усечённый; MicroPDF417, все 34 режима |
| `^BO`, `^B0`, `^BD` | Aztec (включая rune), MaxiCode, режимы 2–6 |

Каждый кодировщик проверяет данные и возвращает диагностику вместо
подмены неподдерживаемого варианта другим штрихкодом. GS1 DataBar composite
(типы 7–12), Aztec ECI и structured append пока не реализованы.
Для Code 128
поддерживаются стандартные режимы Subset B, автоматический режим `A`, строгий
режим числовых пар `C`, GS1-128 режим `D` и управляющие последовательности Zebra.
В режиме `D` скобки и пробелы исключаются из данных, добавляется ведущий FNC1,
а `>8` разделяет поля переменной длины; числовые пары упаковываются автоматически.
Поддерживаются режим `U` и необязательная контрольная цифра UCC Mod 10. GS1
DataMatrix выбирается идентификатором формата `1`; настроенный символ
экранирования поддерживает `x1` для FNC1 и десятичные последовательности байтов
`xdNNN` (например, `|d029` для разделителя GS).

Для обычного ECC200 кодировщик дополнительно использует C40/Text, когда это
позволяет выбрать меньший символ или выполнить явно заданный размер. Проверенные
ASCII/GS1-векторы сохраняются, если они помещаются в выбранную ёмкость.
Полная оптимизация переключений режимов пока не реализована; оставшиеся
различия и точные эталоны перечислены в
`tests/golden/datamatrix-diagnostics/README.md`.
Масштаб `^BQ` также меняет ширину модулей последующих штрихкодов, включая
PDF417; `^BY` переопределяет это значение, а `^BX` сохраняет его.

`^LT` задаёт вертикальное смещение всей этикетки; `^PM` отражает готовую
этикетку по горизонтали; `^LR` меняет режим наложения последующих полей
на обратный (в том числе поверх уже нарисованных полей). `^FR` действует на
одно поле. `^FP` управляет горизонтальным, вертикальным или обратным
направлением текста и межсимвольным интервалом независимо от `^FW`.

`^FO` задаёт верхнюю привязку поля, `^FT` — базовую линию текста, основание
полос штрихкода либо нижний край графики. Парсер сохраняет пропущенные
координаты `^FT` для продолжения предыдущего текста; числовое выравнивание
`0`/`1`/`2` и значение по умолчанию из `^FW` хранятся отдельно от `^FB`.
Эталоны новых команд и позиционирования находятся в `tests/golden/extensions/`
и каталогах соответствующих кодировщиков. PNG получены непосредственно
от Labelary с `X-Quality: Bitonal`; обычная проверка работает без сети.
Если ширина выходного изображения отличается от `^PW`, область печати
центрируется по горизонтали до применения `^PO` и `^PM`, как в Labelary.

Режим GS1-128 `D` проверяется по кодовым словам и пиксельному совпадению с
синтетическими bitonal-эталонами Labelary в обычной и повернутой (`B`) ориентациях.
Эталоны `tests/golden/code128-gs1-*.png` и `font0-block-b-labelary-bitonal.png`
получены 2026-10-07 через API 12 dpmm с размером `1.9737x3.9474` дюйма
(600×1200 точек) и заголовком `X-Quality: Bitonal`. Соответствующие `.zpl`
сохранены рядом; обычные тесты не обращаются к сети. Эталон текстового блока
проверяет привязку и центрирование; полное пиксельное совпадение Font 0 пока
остаётся отдельной нерешённой задачей.

Font 0 рисуется из контуров встроенного Triumvirate Cond Bold. FreeType читает
исходные контуры без hinting, а QPainter заливает их без сглаживания; системный
шрифтовой движок и `QFont::setStretch` в этом пути не используются. Высота и
ширина масштабируются независимо в координатах принтера и ограничиваются
снизу 10 точками, включая размер ячейки для поворотов. Базовая линия `^FO`
равна `floor(0,75 × эффективная высота)`, а `^FT` задаёт её непосредственно.
Повороты учитывают полную высоту и суммарную ширину символов, сохраняя
выносные элементы. Контуры кэшируются в пределах одного вызова рендеринга.

Шаги 304 доступных глифов исправлены по точным числовым метрикам, независимо
проверенным длинными строками в оригинальных bitonal-эталонах Labelary.
Таблица хранит целые числители с знаменателем 2048 и не округляет шаг каждой
буквы до целых точек. Для остальных глифов сохранены метрики встроенного
шрифта. Исходные измерения, ограничения и тесты находятся в
[font0-metrics](tests/golden/font0-metrics/) и
[font0-grid-semantics](tests/golden/font0-grid-semantics/).
Семь пар размеров из этикетки проверяются по синтетическим латинским и
кириллическим `^FO`/`^FT`-эталонам `font0-h*-w*`. Они получены 2026-10-07
через Labelary 12 dpmm, размер `7.89474x3.9474`, `X-Quality: Bitonal`
(2400×1200 точек). Различия сглаживания/привязки контуров к пиксельной сетке
по сравнению с Labelary пока остаются; строгие визуальные тесты не ослаблены.

Сравнение встроенных контуров с Font 0 в PDF Labelary (2026-10-07)
показало различия самих глифов, а не только привязки или общего масштаба.
Например, у `e`, `o` и `g` отличаются контуры. Для ASCII-дефиса `U+002D`
исправлена и форма: используется прямоугольный примитив с отдельно проверенной
привязкой к сетке, сохраняя продвижение 1850/2048 em. Дефис в `hello.zpl`
и 224 поля новых эталонов совпадают попиксельно. Остальные буквы и четыре
малых граничных размера дефиса ещё требуют исправления; ограничения и
измерения приведены в [отчёте о дефисе](benchmarks/FONT0-HYPHEN-2026-10-09.md).
Общее расхождение `hello.zpl` нельзя устранить одним смещением `^FO`.

Проверка `qtzpl_font_glyphs_tests` охватывает 371 уникальный символ:
латиницу и кириллицу обоих регистров, `Ёё`, знаки препинания и распространённые
спецсимволы. Сохранены исходные bitonal-атласы Labelary, добавлены изолированные
обучающие и проверочные атласы, в том числе с разной высотой и шириной,
привязками `^FO`/`^FT` и поворотами. Отчёт `font-glyph-results.json` в
каталоге тестового EXE содержит сравнения отдельных глифов, границы
чернил и число отличающихся пикселей. Для 54 символов, отсутствующих у
Labelary в этом репертуаре, проверяется явная диагностика. Эти тесты фиксируют оставшийся
дефект Font 0, а не разрешают его порогом похожести.

Отдельный [исследовательский набор Font Zero](third_party/font0-native/README.md)
собирается из 12 семейств под OFL 1.1 и собственных контуров. Для каждого
глифа сохраняется происхождение и рецепт редактирования; доступны TTF,
экспорт SVG и визуальный отчёт. Кандидат пока не заменяет встроенный шрифт:
полное совпадение с Labelary не достигнуто. Независимый сплошной корпус
`tests/golden/font0-size-sweep/` проверяет целые размеры 4–512 включительно
при равных высоте и ширине. Его получение и полный прогон запускаются
отдельными инструментами; обычные тесты остаются полностью локальными.

Font A и стандартные подписи Code 128/93, Interleaved/Industrial 2 of 5
используют встроенный производный DejaVu Sans Mono и нативный FreeType.
Генератор `tools/generate_font_a.py`, параметры и лицензия сохранены в
`third_party/font-a-native/`; генерация шрифта не требуется при сборке.
Растеризация применяет TrueType hints до горизонтального растяжения.
На Windows используется FreeType из Qt без дополнительной DLL; если Qt
собран с системным FreeType, CMake требует пакет разработки FreeType.

`^FH` при `^CI28` декодирует последовательности UTF-8, включая смешение
прямого Unicode и шестнадцатеричных символов. Некорректные последовательности
сохраняются в исходном виде с диагностикой `invalid-field-encoding`.

`FieldData` хранит два представления одного поля: `data` для текста и
`std::optional<QByteArray> bytes` для байтовых кодировщиков. `bytes` содержит
данные после `^FH`, но до обработки управляющих последовательностей штрихкода.
При `^CI28` прямой Unicode преобразуется в UTF-8, а hex-последовательности
всегда сохраняют заданные байты. Для остальных `^CI` сохраняется прежнее
однобайтовое представление символов U+0000…U+00FF; это не реализация всех
кодовых страниц Zebra. Если без потерь получить байты нельзя, `bytes` равно
`std::nullopt`; пустое поле имеет доступный пустой массив.

DataMatrix, QR, PDF417, MicroPDF417, Aztec и MaxiCode получают `bytes`
напрямую. Для Unicode в этих штрихкодах указывайте `^CI28`, для отдельных
двоичных байтов — `^FH`. Даже при некорректном UTF-8 точные байты `^FH`
доступны двоичному кодировщику; предупреждение парсера и исходный текст
сохраняются. Текстовые поля и ограничения алфавитов линейных штрихкодов
не меняются. В ручном режиме QR `Bdddd` длина измеряется в байтах.

Добавление `bytes` меняет двоичную раскладку публичной модели: приложения,
использующие библиотеку, нужно пересобрать вместе с ней.

## API для редакторов (0.2)

Библиотека предоставляет данные для последующего подключения Designer.
Сам репозиторий Designer этим пакетом не изменяется. Модель `Document` остаётся
неизменяемым снимком; UUID, undo, группы, таблицы, плейсхолдеры и решение о
возможности визуального редактирования принадлежат приложению.

```cpp
auto document = QtZpl::parse(zpl);
if (!document) return;

auto analysis = QtZpl::analyzeLabel(*document, 0);
auto preview = QtZpl::renderLabel(*document, 0, {.collectFieldGeometry = true});
if (!analysis || !preview) return;

for (const auto& geometry : preview->fields) {
    auto exactFieldSource = document->sourceText(geometry.field.sourceSpan);
    auto boundsInPrinterDots = geometry.clippedBounds;
    // Связь с объектами приложения хранит потребитель.
}
```

### Исходник и данные поля

`Document::source()` владеет полной исходной QString, включая текст вне этикеток,
неизвестные команды и пробелы. Входной `QStringView` нужен только до завершения
`parse`. Копии документа разделяют неизменяемые Qt-данные; возвращённый
`sourceText(span)` view действителен, пока жив его владелец.

`SourceSpan {start, length}` задаёт полуоткрытый диапазон в **кодовых единицах
UTF-16**, а не в байтах файла, Unicode code points или экранных символах.
`sourceText()` проверяет границы и возвращает null view для неверного диапазона.
Пустой диапазон в конце источника допустим. Смещение `-1` обозначает неизвестное
местоположение.

`Command::sourceSpan` сохраняет дословное написание, регистр и CRLF; прежние
`Command::source` и `offset` сохранены. `source` — нормализованное представление,
его длину нельзя использовать для определения конца команды. Обычная лексема
включает разделяющие пробелы/переводы строк до следующей команды; `^FD/^FV`
заканчивается перед `^FS`. Диапазон `^XZ` заканчивается сразу после opcode,
даже если старое нормализованное `source` содержит проигнорированный хвост.
`Label::sourceSpan()` охватывает блок от `^XA` до конца `^XZ`, без межэтикеточного
текста. Восстановленный вложенным `^XA` блок заканчивается перед новым `^XA`,
незавершённый блок — в конце входа. Сохранение полного источника работает и при
`preserveUnknownCommands=false`.

`^CC`, `^CT` и `^CD` меняют префикс команд формата, управляющий префикс и разделитель
параметров соответственно, в том числе между этикетками. Внутри этикетки они
представлены `SyntaxCommand`; `^FH` теперь сохраняется как `FieldHex`.

Каждая из команд `^CC/~CC`, `^CT/~CT`, `^CD/~CD` требует следующий ASCII-символ:
пробел, CR и LF являются значениями, а не пустым параметром. Префикс следующей
команды также поглощается как значение. Это соответствует
[описанию Zebra для CC](https://docs.zebra.com/us/en/printers/software/zpl-pg/c-zpl-zpl-commands/r-zpl-cc-cc.html)
и [Programming Guide, CC/CD/CT, страницы 152/153/166](https://www.zebra.com/content/dam/support-dam/en/documentation/unrestricted/guide/software/zpl-zbi2-pg-en.pdf).
Когда параметра нет в конце завершённого входа или он не является ASCII,
QtZpl сохраняет прежнюю настройку и выдаёт `invalid-syntax-character`; это
восстановление парсера законченного документа, а не ожидание продолжения потока.
Если `^CD` выбрал CR или LF, этот символ сохраняется при разборе параметров;
обычная нормализация переводов строк не удаляет действующий разделитель.

К существующим `FieldData::data` и `bytes` добавлены `rawData`, диапазон payload
`sourceSpan` без `^FD/^FV`, активный `characterSet` и `hexIndicator` (null без
`^FH`). `rawData` сохраняет написание до декодирования. Unicode-текст, точные
байты, ASCII GS, NUL и управляющие маркеры штрихкода не смешиваются: обработку
FNC1/QR-префиксов и других управляющих последовательностей выполняет конкретный
encoder после получения байтов. Эти расширения не меняют смысл `data/bytes`.

### Страницы, анализ и диагностика

`renderLabel(document, index, options)` возвращает одно изображение в `image`
и исходный `labelIndex`. Индекс начинается с нуля. При одинаковых options
изображение равно соответствующему элементу полного `render`, а остальные
полноразмерные растры не создаются и не расходуют бюджет выбранной страницы.
Неверный индекс даёт `invalid-label-index`.

Сохранена текущая семантика состояния: настройки растеризации сбрасываются
для каждой этикетки; `^CI` и синтаксические разделители интерпретируются парсером
по всему потоку. Это не эмуляция постоянной памяти физического принтера.
Ресурсы встроены в библиотеку; загрузка ресурсов из предыдущих форматов не
добавляется неявно.

`analyze` и `analyzeLabel` используют тот же проход применения команд, что и
renderer. Они возвращают `FieldInfo` для текстового/штрихкодового payload,
графической команды или сохранённой неизвестной команды. `settings` содержит
эффективное состояние привязки, шрифта, интерпретации штрихкода, `^BY`, `^FW`,
`^FB`, `^FP`, `^CI/^FH`, `^LH/^LS/^LT`, reverse и преобразования этикетки.
Поля настроек сохраняют семантику команд: нулевые размеры шрифта и пустые
параметры штрихкода могут означать ZPL defaults; окончательная раскладка
представлена геометрией renderer, а не обещанием полностью развёрнутых
параметров каждого encoder.
Для продолжения `^FT` вычисляются метрики текста. Изображения этикеток при
анализе не создаются; штрихкоды не кодируются и графика не распаковывается.
Поэтому успешный анализ не доказывает корректность payload для encoder.

ID поля равен смещению его рисующей команды и уникален только в этом снимке.
Он не является UUID и не гарантирует стабильность после правки источника.
`FieldInfo::sourceSpan` охватывает содержащий поле сегмент до `^FS`
включительно; несколько рисующих команд в одном сегменте имеют разные ID,
но могут иметь общий диапазон. `payloadSpan` у `FieldInfo` указывает на всю
рисующую команду; у `FieldData::sourceSpan` — только на её данные.
`hasUnknownCommands` отмечает неизвестные команды в сегменте, включая
диагностику при отключённом сохранении команд. Ни это поле, ни наличие
геометрии не являются разрешением на визуальное редактирование без потерь.

Оба варианта render и analysis включают все parse-диагностики документа ровно
один раз, затем добавляют диагностику только обработанных страниц. Вызов не
изменяет диагностики `Document`. Машинные `code` и `severity` предназначены
для решений приложения; `message` — для показа. Новые необязательные поля
`labelIndex`, `fieldId`, `sourceSpan` связывают сообщение с исходным снимком,
когда эта связь известна. Parse-сообщения сохраняются как есть, без выдуманного
field ID; ошибка кодирования штрихкода ссылается на его поле и исходную команду
штрихкода. Смещения всегда относятся к полному входу, а не к вырезанной странице.

### Геометрия и системы координат

`collectFieldGeometry=false` сохраняет обычный режим без сбора метаданных.
При включении каждый `FieldGeometry` содержит тот же `FieldInfo` и:

| Поле | Гарантия |
|---|---|
| `logicalBounds` | Прямоугольник раскладки до отсечения: ячейки/блок текста, полный символ с подписью либо размер фигуры/bitmap |
| `paintBounds` | Прямоугольник собственных операций рисования поля до отсечения, включая белый цвет и непрозрачные подложки |
| `clippedBounds` | Пересечение `paintBounds` с выходной этикеткой |
| `anchor`, `baseline` | Привязка ZPL после преобразования этикетки и признак `^FT` |
| `labelTransform` | Преобразование из координат до `^PO/^PM` в итоговые координаты |
| `status` | `Drawn`, `Empty`, `Clipped`, `Unsupported` или `Error` |

Все границы заданы в целых точках принтера в координатах итогового изображения.
`settings.position` остаётся в координатах **до** `^PO/^PM`, уже с учётом
позиционирования, home, shift, top и центрирования `^PW`. Transform и anchor
используют координаты границ ячеек; при отражении это не индекс центра
растрового пикселя (`width-x`, а не `width-1-x`). `baseline` обозначает семантику
привязки, а не вторую систему единиц. DPI не масштабирует геометрию.

Границы описывают собственное поле до перекрытия другими полями. Они
сохраняются для белых фигур и reverse. `clippedBounds` — прямоугольное
обрамление, а не маска чернил; оно может включать пробелы или отверстия.
`Drawn` означает, что операции поля пересекают холст по этому обрамлению,
а не что поле различимо на фоне после композиции. `Clipped` означает пустое
пересечение непустого `paintBounds`. Состояние `Empty` не удаляет объект
редактора. Для ошибочного поля fallback остаётся политикой приложения.

### Графика, бюджеты и потоки

`decodeGraphic(GraphicField, GraphicDecodeOptions)` возвращает `DecodedGraphic`
с размером, `bytesPerRow` и packed bitmap `bytes` (старший бит первый).
Используется та же реализация, что при рендере. Поддержаны обычный и сжатый
ASCII, Z64 с CRC16 и бинарный `B`; режим `C` возвращает
`graphic-field-compression`. Неполная последняя бинарная строка дополняется
нулевыми байтами; неполная ASCII-строка ошибочна, пропущенные полные конечные
ASCII-строки остаются пустыми согласно прежней семантике. Z64 распаковывается
в ограниченный буфер: поддельный размер не разрешает рост аллокации.
Пример: `auto bitmap = QtZpl::decodeGraphic(graphic);` без искусственной этикетки.

Все лимиты неотрицательны; ноль запрещает соответствующий расход, а не
отключает проверку. Значения по умолчанию:

| Options | Лимиты |
|---|---|
| `ParseOptions` | 16 Mi UTF-16 units источника, 1 000 000 лексических команд (в том числе вне форматов), 10 000 этикеток, 10 000 диагностик |
| `RenderOptions` | 256 Mi выходных пикселей суммарно, 64 MiB распакованной графики суммарно, 10 000 диагностик вместе с parse |
| `GraphicDecodeOptions` | 64 MiB результата с учётом дополнения последней строки; 128 MiB закодированного входа до CRC/Base64 |

Бюджет источника проверяется до копирования, команд/этикеток — до добавления,
выходных растров и графики — до выделения. Прежние жёсткие ограничения
размеров и промежуточных растров сохраняются: повышение общего бюджета их
не отключает. Анализ без растров не расходует бюджеты пикселей/распаковки.
Превышения возвращают `parse-source-limit`, `parse-command-limit`,
`parse-label-limit`, `parse-diagnostic-limit`, `render-pixel-limit`,
`render-graphic-limit`, `render-diagnostic-limit`, `graphic-byte-limit` или
`graphic-input-limit`.
Отрицательные лимиты дают соответствующую ошибку `invalid-*-options`.

Options содержат `std::stop_token stopToken`. Отмена кооперативная: проверки
выполняются при входе, между командами, в длинных проходах парсера и порциях
распаковки. Внутренний encoder/рисование отдельного поля не прерывается
насильно. Запрошенная отмена возвращает `operation-cancelled`; частичное
изображение не публикуется как успешный результат. Глобальный кэш не добавлен;
его необходимость и размер следует определять по измерениям потребителя.

Для render и analysis сначала создайте `QGuiApplication` в главном потоке и
сохраняйте его до завершения рабочих вызовов. Один неизменяемый `Document`
можно одновременно передавать в render/renderLabel/analyze/analyzeLabel.
Время его жизни должно охватывать вызовы. Каждый вызов владеет своим контекстом
шрифтов и результатом; изменение полученного QImage не меняет другие результаты.
Parse и decodeGraphic не требуют GUI. Проверены первый конкурентный запуск
и повторные вызовы. Поддержка команды парсером, точность её растра и
возможность визуального редактирования — разные свойства.

### Совместимость и проверки потребителя

Версия **0.2.0** сохраняет существующие функции и начальные поля агрегатов,
но расширяет публичные структуры и `CommandPayload`: это **изменение ABI**.
Shared- и static-потребителей необходимо пересобрать вместе с библиотекой.
Для версий до 1.0 CMake package compatibility ограничена minor-версией,
SOVERSION включает major/minor; старую DLL нельзя подставлять к новым headers.

`qtzpl_inspect` демонстрирует parse, анализ, отдельную страницу, геометрию и
декодирование bitmap через публичный header:

```text
build_agent\build_agent_debug\examples\qtzpl_inspect.exe input.zpl 0 preview.png
```

Потребительские регрессии находятся в `tests/test_designer_api.cpp`, контракты
исходника — в `tests/test_parser_contract.cpp`, векторы bytes/Unicode — в
`tests/test_field_data.cpp`. Обычные проверки не используют сеть. Пакеты
рекомендаций L0–L6 реализованы в библиотеке; подключение L7 в Designer
оставлено отдельной работой по явному ограничению текущей задачи.

## Сборка

Используется последний поддерживаемый диалект C++: MSVC — `/std:c++latest`,
остальные компиляторы — новейший стандарт, поддерживаемый компилятором и
известный CMake, не ниже C++23. Значение CXX23 в метаданных CMake для MSVC
сохранено для совместимости с CMake 3.30; режим компиляции задан явно.

### Windows (рекомендуется)

Скрипт `tools/build_helper.py` сам поднимает окружение Qt 6.11 и MSVC 2022 и
вызывает CMake/Ninja.

**Без параметров** — собирает Debug и Release в отдельных каталогах, без тестов:

```text
py -3 tools/build_helper.py
py -3 tools/build_helper.py all --clean
```

Все каталоги сборки и сгенерированные артефакты находятся внутри `build_agent/`.
Стандартные каталоги: `build_agent/build_agent_debug`, `build_agent/build_agent_release`.
Прежние корневые `build_*` перенесены туда с сохранением имён; корневой
`build/` соответствует `build_agent/build/`. После переноса CMake-сборке
нужна свежая конфигурация: абсолютные пути в старом кэше не переносятся.

**Одна конфигурация** — укажите `--config` (каталог подбирается автоматически):

```text
py -3 tools/build_helper.py all --clean --config Debug
py -3 tools/build_helper.py test --config Debug
py -3 tools/build_helper.py build --config Debug --target QtZpl

py -3 tools/build_helper.py all --clean --config Release
py -3 tools/build_helper.py build --config Release --target QtZpl
```

Подробный протокол QtTest сохраняется в `build_agent/build_agent_debug/tests/test_results.txt`
(или в соответствующем каталоге другой конфигурации), включая строки ошибок.

Свой каталог сборки также должен находиться внутри `build_agent/`:

```text
py -3 tools/build_helper.py build --config Release --build-dir build_agent/build_custom
```

Повторная сборка без переконфигурации:

```text
py -3 tools/build_helper.py build --config Debug
py -3 tools/build_helper.py build --config Release
```

### Установка в другой проект

```text
set QTZPL_ROOT=C:\QtZpl\Release
py -3 tools/build_helper.py install --clean --config Release --build-dir build_agent/build_agent_release --install-prefix C:\QtZpl\Release
```

Debug-установка — `--config Debug`. Другой kit Qt — `--qt-version` и `--compiler`.

### Ручная сборка (CMake)

Если окружение Qt и MSVC уже настроено в терминале:

```text
cmake -S . -B build_agent/build_debug -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_PREFIX_PATH=C:/Qt/6.11.2/msvc2022_64
cmake --build build_agent/build_debug
ctest --test-dir build_agent/build_debug --output-on-failure

cmake -S . -B build_agent/build_release -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_PREFIX_PATH=C:/Qt/6.11.2/msvc2022_64
cmake --build build_agent/build_release
```

По умолчанию в `build_helper.py` используется Qt **6.11.2**, комплект **msvc2022_64**.
Параметры `--qt-version` и `--compiler` переключают другой kit из `C:\Qt`.

### Сравнение с Labelary golden

Утилита `qtzpl_compare_golden` рендерит ZPL и сравнивает результат с эталонным
PNG (ink bounds, число расхождающихся пикселей, Jaccard, diff-overlay):

```text
py -3 tools/build_helper.py build --config Debug --target qtzpl_compare_golden

build_agent\build_agent_debug\examples\qtzpl_compare_golden.exe ^
  tests\corpus\go-zpl-demo\hello.zpl ^
  tests\golden\go-zpl-demo\hello-page-1-labelary-bitonal.png ^
  build_agent\build_agent_debug\hello-actual.png ^
  build_agent\build_agent_debug\hello-diff.png ^
  --width 812 --height 609 --dpi 203 --ignore-label-home
```

Параметры `--width`, `--height`, `--dpi` и `--ignore-label-home` берите из
`tests/corpus/go-zpl-demo/manifest.json` для соответствующей фикстуры. На
2026-10-09 для `hello.zpl` QR и общие границы чернил совпадают с Labelary,
но контуры Font 0 дают 805 отличающихся пикселей; см. `AGENTS.md` и
[отчёт проверки NORTHLINE](benchmarks/NORTHLINE-RASTER-2026-10-09.md).
